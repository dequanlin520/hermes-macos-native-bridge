# M12-002 Reproducible RC and Provenance Verification

M12-002 verifies that a Hermes Bridge release candidate can be rebuilt twice
from one exact source commit in isolated source clones, then records artifact
inventory, provenance, and reproducibility evidence under `artifacts/m12-002/`.

The verification entry point is:

```sh
HERMES_RC_VERSION=0.1.0-rc.1 Scripts/m12_002_reproducible_rc_provenance.sh
```

## Reproducibility definition

An RC is reproducible for M12-002 when two independent clean clones of the same
commit produce the same production payload topology and the same normalized
payload content for the same explicit RC version.

The verification does not create a packaging system. Each rebuild invokes the
existing M12-001 assembly flow:

```sh
Scripts/m12_001_release_candidate_assembly.sh
```

## Exact versus normalized comparisons

The verifier compares these fields exactly:

- RC version and RC archive filename version.
- Source commit recorded in both release manifests.
- Bundle identifiers.
- XPC protocol version.
- Component version inventory.
- SBOM package names and version information.
- Checksum manifest validity.
- Production payload topology: relative path, file type, executable bit, bundle
  role, and production/test classification.

The verifier compares these fields after normalization:

- `Info.plist` content parsed as property-list data and serialized with stable
  JSON key ordering.
- Release manifest content with volatile build timestamp, branch metadata, and
  executable artifact hashes removed from the stable comparison.
- Mach-O executable metadata with UUIDs, code signature offsets, and temporary
  source paths scrubbed.
- Ad-hoc signature files and code signature resources as allowed signing
  byproducts.

Unexplained normalized differences fail the verification and prevent signing
promotion.

## Allowed nondeterminism

M12-002 permits only documented nondeterminism:

- Release manifest build timestamp.
- Archive container timestamp and gzip metadata.
- Mach-O `LC_UUID` generated by the Apple toolchain.
- Ad-hoc signature blobs and derived `CodeResources` hashes.
- Temporary paths from the artifact-owned clean clones.

These differences are recorded in `artifacts/m12-002/differences.json`.

## Provenance format

`artifacts/m12-002/provenance.json` is an in-toto/SLSA-inspired JSON statement.
It is intentionally not a claim of an official SLSA level.

The document records:

- Product and RC version.
- Source repository identity, exact commit, and branch as informational
  metadata.
- Build command and input materials.
- Builder and tool versions.
- Target architecture and minimum macOS version.
- XPC protocol version.
- Signing and notarization state.
- Output artifacts and SHA-256 hashes.
- Reproducibility result and allowed nondeterministic fields.
- Source cleanliness and production-isolation security findings.

## Clean-worktree guarantees

The script creates two artifact-owned clean local clones under
`artifacts/m12-002/worktrees/`. Each clone checks out the same detached commit
and is rejected if `git status --porcelain --untracked-files=all` reports any
source changes before the build starts.

The developer checkout may contain unrelated untracked artifacts. Those files
are not consumed by the clean clones. The script removes only its own
`artifacts/m12-002/worktrees/` directory during cleanup.

## Swift/Xcode reproducibility limitations

Unsigned and ad-hoc-signed Swift/Xcode builds can include nondeterministic
Mach-O UUIDs and signature data. M12-002 therefore proves reproducibility at
the production topology and normalized payload level. It does not claim that
raw executable bytes are bit-for-bit identical unless the exact-difference
report shows no executable-byte drift.

Archive byte equality is also not required because gzip and tar container
metadata can vary independently from the normalized payload.

## Promotion criteria

`READY_FOR_SIGNING_PROMOTION=yes` requires:

- Both clean rebuilds complete successfully.
- RC version, source commit, manifest, SBOM, checksum, app/service version, and
  XPC protocol checks pass.
- Production payload topology and normalized payload content match.
- No unexplained normalized differences exist.
- No acceptance support, tests, fixture backends, sentinel secrets, developer
  paths, credentials, tokens, or private keys are exposed.
- Isolated worktrees are cleaned and no residual process is reported.

Signing and notarization promotion may proceed only after this result is `yes`
and the M12-001 RC remains ad-hoc or unsigned pending the dedicated signing and
notarization gate.
